# Changelog

All notable changes to sandcast are recorded here.
Changing a pin below requires an entry in this file.

## Unreleased

### Field feedback fixes (feature 002-field-feedback-fixes)

Fixes for the eleven issues from the first real builds ([#1](https://github.com/sandcast-dev/sandcast/issues/1) to [#11](https://github.com/sandcast-dev/sandcast/issues/11)).

#### The image matches its inputs (#1, #2, #3)

- The lockfile decides tool versions: a mise component that the base image provides at a version other than the one `mise.lock` locks for the target platform, or at a version the probe cannot read, is planned as `shadow` and installed at the locked version; an equal version stays `skip`. There is no per-component opt-out. The delta records `locked_version`.
- The probe records every `PATH` hit of a component's primary binary (paths not resolved; every binary with resolved targets is follow-up T060). For the OpenShell target, a binary whose every hit lies under the overmount home of the base image (the registry entry's `overmount_home`, `/sandbox` by default) counts as missing and is re-provisioned to a persistent location, reported as a relocation notice of feature 003 (`reprovisioned`, or `hidden` when no definition or fragment can install it and it stays unresolved); when only the first hit lies there, another copy decides and its version counts as unknown. The delta records `ignored_paths`. The container target is unchanged.
- New plan notices with a stable `<kind>: <subject>: <message>` form, sorted after the other notices: `lockfile-shadow`, `unknown-version`, `workspace-path` (the first `PATH` hit of a tool lies under the overmount home while another copy decides), `home-rc-path` (container target only: a home rc file of the base image resets `PATH`; in OpenShell images no shell reads a home rc file, so none is reported) and `reference`. `sandcast build` repeats them in its report (`notices`).
- `sandcast components match` reports `pinned_versions` (value, file, `exact`, `range` or `channel`) from `go.mod`, `go.work`, `rust-toolchain.toml`, `rust-toolchain`, `.python-version`, `pyproject.toml`, `.nvmrc`, `.node-version`, `package.json`, `.tool-versions` and `mise.toml`, a `PINNED` table column, and `notes` for pin files it cannot parse. `.tool-versions` and `mise.toml` entries count as evidence.

#### Sessions get the curated shell (#11)

- `/etc/profile.d/sandcast-env.sh` replaces `/etc/profile.d/sandcast-mise.sh`. It exports every `MISE_*` setting and the component, harness and relocation environment (for example `RUSTUP_HOME`, `GOPATH`, `CLAUDE_CONFIG_DIR`, `ZDOTDIR`) and puts the mise shims first on `PATH`, followed for the OpenShell target by the base image's `PATH` directories beyond `/usr/local/bin:/usr/bin:/bin` (recorded by the probe as a new `path` fact; the probe cache moves to format 3), except directories under the overmount home, which the mounted workspace hides and which may hold untrusted project content: they never reach a session `PATH` nor the image `PATH` that OpenShell's default agent inherits, and neither does a `PATH` entry that is not absolute (`.`, `bin`, `~/.local/bin`), which resolves into the workspace as well (the plan writes the image `PATH` without them, filtering a component `PATH` the same way with a notice); the script drops every such entry from an inherited `PATH` once per session, before `_sandcast_path` runs, and exports `SANDCAST_PATH_STRIPPED` so that a child shell keeps a directory under the home the session put on `PATH` later, such as an activated virtual environment; the plan reports each left-out entry as a `workspace-path` notice, and a virtual environment there joins the `PATH` only when it is activated (a tool that reads the base image's `VIRTUAL_ENV` may use it regardless; see the build guide's known limitations). Every entry point of an OpenShell session sources it before the shell is replaced: a login shell through `/etc/profile`, the shell hooks of feature 003 (the login hook and the block at the top of the system bashrc), the bash and sh launchers, and the global zshenv block. In bash the script also re-applies the shims through `PROMPT_COMMAND` and, for `bash -lc`, a self-removing `DEBUG` trap; that repair matters on the container target, where a directly started bash still reads the image home's rc files; in OpenShell images no shell reads a home rc file, so it only puts the shims first again after a curated rc that changed `PATH`.
- Every build, on both targets, removes the shell hooks of a previous sandcast build from the base image (the login hook file and the block at the top of the system bashrc) before it writes its own, so a container image layered on an OpenShell image does not keep them; removes the first layout's `/etc/profile.d/sandcast-mise.sh` when it carries sandcast's header; and removes a session environment script of a previous build when this build installs none, which is never the case for an image that uses mise tools, installed by this build or kept from a sandcast-built base (the script is written again instead). `build.log` records each removal.
- In a zsh image (`shell.program: zsh`, or a `zsh` component without a shell section), the shell hooks of feature 003 hand an interactive terminal session that OpenShell starts in bash to the curated zsh (`/bin/zsh -i`, or `zsh -l -i` for an interactive login bash), the final user's login shell is `/bin/zsh` for created and kept users, and the zsh new-user wizard is disabled. `SANDCAST_NO_SHELL_SWITCH=1` in the sandbox environment keeps bash: the hooks then start `bash --noprofile --norc -i` with the session environment, which reads no startup file from the workspace home either. An image whose base image ships zsh without zsh being the curated shell gets the zshenv block too: on the OpenShell target a zsh the user starts never reads a workspace `.zshrc`, on the container target it keeps the image home's own startup files. On the container target a zsh plan sets a kept user's login shell to `/bin/zsh` as well.
- The curated rc (`/opt/sandcast/zdotdir/.zshrc` or `/opt/sandcast/bashrc`, see feature 003) starts with two lines that re-apply the shims and mark the file as read.
- `sandcast verify` (and `build --verify`) always adds session checks for the OpenShell target: every component check runs again under OpenShell's cleared environment through `bash -lc`, `bash -i` and, with zsh, `zsh -il -c`, plus a startup check of the selected shell. The hooks replace these shells as in a real session, so `bash -i` runs the check in the curated shell (zsh, the bash launcher, or bash without startup files), which reads it from stdin with the same positional parameters, and no home rc file runs. Each session check first requires every binary of the component that resolves in the image environment to resolve through the session `PATH`; a binary that does not resolve there either is skipped and reported in `notes`. Results carry a `condition` and count toward the exit status; the console shows them in a `session checks` group.

#### The image reaches the gateway (#8, #9, #10)

- The build report adds `image_ref`, `sandbox_create` (`openshell sandbox create --from <ref>`), `pushed` and `digest`; `build.log` records the push. The engine reads the registry digest with `podman push --digestfile` or from docker's push output.
- `sandcast init` takes `--image name[:tag]`, `--platform` and `--push`, and explains that the default `localhost/<name>` works only with a local gateway that shares the engine's image storage.
- `sandcast manifest validate` reports `warnings` (console `warning:` lines) for a Docker Hub reference without a namespace; `valid` and the exit status are unchanged, and plan repeats it as a `reference` notice.
- Runtime notices that never enter the plan file: `emulation` (a component with the new `emulation_unsafe` field, set on `rust`, in a build whose platform differs from the engine host's architecture), `gateway` (a `localhost/` image while the active `openshell` gateway is remote; also in the `profiles import` report as `warnings`) and `docker-hub` (anonymous pull rate limits after a push to `docker.io`).
- New guide `docs/guides/cross-arch.md`: Rosetta in the podman machine, a remote amd64 podman connection (`CONTAINER_CONNECTION`, SSH identity limits, the socket-forward workaround, the macOS socket path limit) and CI.

#### Capture works from facts the binary reports (#3, #4, #5, #6, #7, #11)

- Manifest component entries can declare `bins` for components that no tier defines: verify checks them, the conflict check includes them, `sandcast promote` defaults `--bins` to them and then removes them from the manifest entry, and validation and plan reject `bins` on a tier-defined key.
- `sandcast harness discover` marks every skill and plugin `portable` (with a `reason` when not) and proposes plugins whose local marketplace directory is a git checkout with a remote, with a `remote` object (`url` without credentials, `unpushed_commits`, `uncommitted_changes`, `name_match`). Discovery reads local git state only and never fetches.
- Skill snippets run unchanged in sh, bash and zsh, remove their temporary file on every path and propagate the exit status of `sandcast`; a test runs every snippet under the three shells.
- The capture skill proposes exact pinned versions, asks where the image runs and passes `--image`, `--platform` and `--push` to init for a remote gateway, bases its copy offer on the portability marker, presents remote notes for proposed marketplace plugins, and loads a tool's own zsh completion before a kept `compdef` line whose plugin was removed. The build skill declares `bins` instead of adding symlinks.

#### Compatibility

- Probe cache format 3 (format 2 added binary paths and home rc facts, format 3 the base image `PATH`): the first plan after the upgrade runs one full re-probe per base image.
- Skill bundle 0.2.1 (0.2.0 described the session environment and pinned versions, 0.1.4 the bounded dotfile sources; 0.2.1 describes the merged shell model): `sandcast skills check` reports installed skills as outdated; run `sandcast skills install`.
- Images with `shell.program: zsh` now hand interactive terminal sessions from bash to zsh, and no OpenShell session reads a startup file from the workspace home. Set `SANDCAST_NO_SHELL_SWITCH=1` in the sandbox environment to stay in bash.
- Images with a base tool at another version than `mise.lock` now install the locked version and grow accordingly.
- The `engine.Engine` interface gains `HostArch`, and `Push` returns the registry digest.
- Pins unchanged: OpenShell v0.1.3, mise v2026.10.4, manifest schema 1, plan schema 1.

### Runtime home model and shell initialization (feature 003)

- The interactive environment now survives the OpenShell workspace mount over the home. Everything is baked outside the home and programs are pointed at it through environment variables: zsh sets `ZDOTDIR=/opt/sandcast/zdotdir` in the global zshenv, written to both `/etc/zsh/zshenv` (Debian and Ubuntu) and `/etc/zshenv` (other builds), and as image `ENV`, so it holds when a runtime clears the environment; bash uses a baked `/opt/sandcast/shell-login` launcher that runs `bash --noprofile --rcfile /opt/sandcast/bashrc` (without `--norc`, which would make bash ignore the rcfile) and is the login shell and `CMD`, also for a user kept from the base image (`usermod -s`, with a passwd fallback); any other login shell gets a baked `/opt/sandcast/sh-login` launcher that points `$ENV` at `/etc/profile.d/sandcast.sh` and execs a non-login `/bin/sh`. Both launchers drop `-l` and `--login` from the forwarded options (`-ilc` becomes `-ic`), so a caller that asks for a login shell (`su -l`, an editor's environment probe) cannot make the shell read a workspace `.profile` or `.bash_logout`, and the bash launcher keeps its rcfile. The bash launcher exports the pid guard the bashrc hook recognizes only when its bash will be interactive; a `shell-login -c 'cmd'` run removes it, so an interactive bash that the command execs with the same pid still goes through the hook. Because OpenShell starts `/bin/bash` itself after clearing the environment (`-i` for terminals, `-lc` for `sandbox exec`, `-l` for its default agent), OpenShell images also carry two hooks: `/etc/profile.d/zz-sandcast-shell.sh` replaces a login bash before it reads a home profile or logout file (keeping the command, arguments, options such as `-e`, `-u`, `-x` and `-o pipefail`, and the exit status; a script is passed after `--` and a renamed bash still reads its input) and redirects `HOME` for other POSIX login shells, and a block prepended to the system bashrc hands an interactive bash to the curated shell before it reads `~/.bashrc`. Both source the session environment script (`/etc/profile.d/sandcast-env.sh`, which carries the relocation variables), and in a zsh image export `SHELL=/bin/zsh` (the global zshenv too), so tmux and editor terminals that start `$SHELL` from the curated zsh get zsh rather than a bare nested bash. A hook block or `ZDOTDIR` export left by a previous sandcast build (a base image sandcast built, or a rebuild) is replaced, with a line in `build.log`, never kept, and the blocks and curated rc files of the pre-release spec 002 layout are removed from a layered base the same way. The build bakes the absolute path of the image's bash into the launcher, so an explicit `/bin/bash` handed to it by a hook never resolves bash through a `PATH` that the curated rc extended with the workspace `$HOME/bin`. When the curated shell cannot be executed, an interactive session prints one `sandcast:` line naming the target and the `/opt/sandcast` policy grant and continues in `bash --noprofile --norc` instead of ending with status 126. The image policy grants `/opt/sandcast` read-only. bash builds without a system bashrc (Fedora, RHEL) cannot be hooked for interactive non-login shells; the build guide lists this limitation.
- A startup file in the mounted workspace home (a committed `.zshrc`, `.bashrc` or `.profile`) is never auto-sourced, closing a code-execution vector for untrusted projects.
- New manifest `dotfiles` field: capture proposes a bounded host-home allowlist (git, starship, tmux, readline) and accepts explicit paths. Each dotfile is redacted and relocated outside the home to a location its tool reads natively (`/etc/gitconfig`, `/etc/tmux.conf`, `/etc/xdg/...`) or one named by a tool-specific variable (`STARSHIP_CONFIG`, `INPUTRC`; the baked inputrc includes `/etc/inputrc`). `XDG_CONFIG_HOME` is never set image-wide, so tools such as `gh` can still write their configuration. Colliding entries dedup deterministically (explicit wins) with a notice, except git's two files: `~/.config/git/config` and `~/.gitconfig` are merged into `/etc/gitconfig` in git's order, so both take effect and `~/.gitconfig` values win. Sources are bounded so a committed manifest cannot pull host secrets into an image: from the home only allowlist entries and, under `~/.config`, the configuration of known tools (`git/`, `starship.toml`, `nvim/`, `helix/`, `tmux/`, `alacritty/`, `kitty/`, `wezterm/`, `ghostty/`, `bat/`, `ripgrep/`; the rest of `~/.config` holds credential stores no redactor recognizes reliably and is refused, with a notice that names the bound), otherwise only files that resolve inside the project; credential stores (`.ssh`, `.aws`, `.gnupg`, `.kube`, `.docker`, `.config/gh`, `.config/sops`, `.config/op`, `.config/gcloud`, `.config/containers`, `.config/rclone`, `.config/hcloud`, `.config/doctl`, `.config/wrangler`, `.config/helm/registry`), `.netrc`, history files and credential-looking names in any path segment are refused without regard to case, before and after following symlinks; only regular files up to 256 KiB are read. The redactor also recognizes age secret keys (`AGE-SECRET-KEY-1...`). A generic dotfile keeps the part of its source path below a `.config/` segment wherever that segment sits, so a project copy such as `dotfiles/.config/nvim/init.lua` lands at `/etc/xdg/nvim/init.lua`, where XDG consumers search. Capture proposes an allowlist entry only within the same bounds (the whole path is resolved, so a symlinked `~/.config` that leaves the home is caught), reports an entry it cannot check (an unreadable parent directory) instead of treating it as absent, and `sandcast components match` reports a host home it cannot determine instead of proposing nothing silently. An entry outside the bounds, missing or unreadable, or whose relocation target would carry shell metacharacters, is skipped with a notice rather than baked.
- The plan reclassifies a base-image tool found only under the overmount home as missing and re-provisions it to a persistent location, reporting every relocation and re-provision as a notice. The decision is made at plan time from the probe's `PATH` hits (cache format 3, see above). The plan fails when anything it bakes or declares would lie under the overmount home: shell files, dotfile targets, component and harness directories, and component, harness and fragment policy paths.
- A registry entry may set `overmount_home` (openshell entries only, default `/sandbox`): the `WORKDIR` sandcast writes, which the OpenShell podman driver mounts the workspace over (the Kubernetes driver of v0.1.3 always mounts at `/sandbox`, so another value is for the podman driver only, and the plan prints a notice). The plan records the effective value as `base_image.overmount_home`, which the `WORKDIR`, the workspace directory, the re-provisioning and the guard all use. A well-known system directory, or a path below one (except a subdirectory of `/home`), is refused, because the build hands the workspace directory to the final user.

### OpenShell pin refresh v0.1.2 to v0.1.3

- Re-vendored the upstream provider profiles from OpenShell v0.1.2 (commit 6648bd0c) to v0.1.3 (commit e1f3c82c). The 16 existing profiles are byte for byte identical; `oci-genai` is new, for 17 in total.
- Default sandbox policy moved from `policy/default-v0.1.2.yaml` to `policy/default-v0.1.3.yaml`; `restrictive_default_policy()` content is unchanged between the two releases.
- Ported the v0.1.3 stable profile validation into `internal/profile`: credential names and token_grant endpoint and audience-override selectors must be free of control characters; a token_grant endpoint may not use protocol `sql` or `tls: skip`; `2026-07-28` joins the supported MCP protocol revisions (the default revision stays `2025-11-25`); and a null value at a schema-declared object path is rejected before typed decoding.
- Relaxed the `sandcast profiles import` version check: it now accepts any `openshell` CLI release on the pinned minor line (any `0.1.x` for the v0.1.3 pin, pre-release suffixes included) instead of an exact match, so a future patch release needs no code change.
- Deferred to a follow-up: the experimental `ProviderFileProfile` (`files`) feature and the token_grant audience-override to endpoint binding-conflict checks, both of which upstream marks as subject to change.

### Probe watchdog (#16)

- Each probe and verify check is bounded on busybox and coreutils images alike. busybox `timeout(1)` signals only the check's own shell, so a process the check started kept the output pipe open past the limit. When `timeout(1)` is missing or is not coreutils and `setsid(1)` and `sleep(1)` exist, each check now runs in its own session and a watchdog sends `SIGTERM` to the whole process group after the limit; the watchdog reports that it fired, so a check that traps `SIGTERM` is still marked as a timeout (exit 143). Images with `setsid` and `sleep` but no `timeout(1)` now get the limit and the timeout marking. On the coreutils path `timeout(1)` runs as a background job. On both paths whatever is left of the check's process group after its shell exits is killed with `SIGKILL`, so it cannot hold the output open.
- The integration job runs on ubuntu-26.04 (podman 5) and fails early on older podman, whose 4.9.3 rejects heredoc `RUN` instructions.

### Build push override

- `sandcast build --push=false` now skips the push of a target with `push: true`. The `--push` flag overrides the target field `push` whenever it is given; without the flag the target field decides. Before, the two were combined with a logical or, so a manifest with `push: true` always pushed.

### mise shims ignore project mise files (002 T059)

- The image sets `MISE_OVERRIDE_CONFIG_FILENAMES=/etc/mise/mise.toml` and `MISE_OVERRIDE_TOOL_VERSIONS_FILENAMES=none` in the `30-mise` layer and in the session environment script, so a shim run inside a project with a `mise.toml`, `.mise.toml`, `.mise/config.toml` or `.tool-versions` keeps the image configuration. Before, a project pin missing from the image lockfile made every shim print `mise WARN ... is not in the lockfile`, and a pin of another version of an image tool left its shim with no version (`mise ERROR No version is set for shim`). `MISE_ENV` still selects a `mise.<env>.toml` when a user sets it.
- `sandcast verify` adds the session check `session.mise.project-config` for the OpenShell target when mise installs a checked component: the first such component check runs in a login bash from a project directory that pins every image tool to a version the lockfile lacks, and fails on any `mise WARN` or `mise ERROR` line other than mise's update notice.
