## Findings

### Important

- [x] **Important** I-1 (resolved: fixed in skills/build/SKILL.md (promotable fragment shape, promote exit 2 handling)) `skills/build/SKILL.md:114`, L125, L206-217: the fragment rules allow `ARG`, `COPY` and `LABEL`, and L125 implies a second `RUN` under `USER <final user>` for post-install commands, which also breaks "Exactly one `RUN`" on L114. `sandcast promote` converts only `RUN`, `USER`, `ENV` and `WORKDIR` and refuses fragments that mix root and final-user `RUN` steps (`internal/build/promote.go:161`, `:165`). Tested: a fragment with `ARG`/`LABEL` and a fragment with a final-user post-install `RUN` are both stored by `fragments write`, and `promote` exits 2 for both. `COPY` also has no usable source: the build context `.sandcast/build/<target>/` holds only sandcast-generated files and the skill may not write there. Step 5 then offers a promotion that cannot succeed and never says what to do on exit 2. Fix: on L114 allow only `RUN`, `USER`, `ENV` and `WORKDIR` and say why (promotion); replace L125 with "run post-install steps inside the single root `RUN` as `su <final_user.name> -s /bin/sh -c 'HOME=<final_user.home> <cmd> <non-interactive flags>'` after creating and chowning the directories, or write the whole fragment as the final user when nothing needs root"; in Step 5 add "If `sandcast promote` exits 2, show its message, keep the fragment active, and do not retry with `--yes`."
- [x] **Important** I-2 (resolved: fixed in skills/build/SKILL.md (configuration under /etc or /opt through env vars, caches in /tmp)) `skills/build/SKILL.md:124-125` against L123: the directory ownership rule (examples `.cache`, `.config`) and the post-install rule put files in the final user's home, but the default OpenShell base image `nvidia-community-base` runs as `sandbox` with home `/sandbox` (`base-images.yaml:14`), and L123 forbids anything under `/sandbox` because the Kubernetes driver mounts the workspace volume over it (plan.md R-10). The skill gives contradictory instructions for every tool that needs configuration. Fix: add to L124-125 "Read `final_user.home`. When it is `/sandbox` or below it, nothing written to the home survives on Kubernetes: put configuration under `/etc/<key>` or `/opt/<key>` and point the tool there with an `ENV` the tool supports (for example `<TOOL>_CONFIG_DIR`); if the tool insists on the home directory, tell the user its configuration is lost on the Kubernetes driver instead of writing it."
- [x] **Important** I-3 (resolved: fixed in both skills ("Any other failure: show the output and stop.")) `skills/build/SKILL.md:36-38`: Step 1 handles exit 0, exit 3 and a missing command, but not any other failure. The capture skill has that branch (capture L35). With the current binary, `sandcast skills check --harness claude-code` exits 2 (`no adapter for harness "claude-code"`), and the build skill gives no instruction, so the version gate (FR-004) can be skipped. Fix: add "Any other failure: show the output and stop." after L38.
- [x] **Important** I-4 (resolved: fixed in skills/build/SKILL.md (two RUN forms) and internal/build/promote.go (shell heredocs kept whole)) `skills/build/SKILL.md:111-128`: the fragment rules say nothing about heredocs, although the validator and promotion treat them specially. Tested: `RUN cat <<'EOF' > /etc/toold.conf` is stored, and `promote` exits 0 with a recipe whose script is only the heredoc body (`color = true`), marking the working fragment superseded; `RUN bash -euxo pipefail <<'EOF'` is promoted with `bash -euxo pipefail` dropped, so the recipe runs the body under `/bin/sh` without `pipefail`. Fix: add a rule "Use backslash continuation as in the example. If you use a heredoc, write exactly `RUN <<'EOF'` alone on the line, start the body with `set -eux`, and end it with `EOF` alone on a line. Never put a command on the heredoc `RUN` line (`RUN cat <<EOF > file`, `RUN bash <<EOF`); write files with `printf` inside the `RUN` instead." See also code observation C-1.
- [x] **Important** I-5 (resolved: fixed in skills/capture/SKILL.md (completion scripts trigger compinit)) `skills/capture/SKILL.md:133`: the `compinit` trigger is only a literal `compdef` or `zstyle ':completion:*'` in the curated text. Brainstorm 072 change 13 also covers "other completion-dependent directives". Completion scripts that the configuration sources or evaluates (`source <(kubectl completion zsh)`, `eval "$(gh completion -s zsh)"`, files starting with `#compdef`) call `compdef` and print `command not found: compdef` at every shell start when a stripped plugin manager was the only source of `compinit`. Fix: extend the trigger to "the configuration contains `compdef`, `zstyle ':completion:*'`, or sources or evaluates a completion script (`<cmd> completion zsh`, `#compdef`), or a stripped plugin manager loaded `compinit`".

## Code observations surfaced by this review (not skill defects)

- [x] **Important** C-1 (resolved: fixed in internal/build/promote.go with TestPromoteShellHeredocKeepsCommand) `internal/build/promote.go:144-150`: a heredoc `RUN` keeps only the heredoc body and drops the command on the `RUN` line, so `RUN cat <<'EOF' > file` and `RUN bash -euxo pipefail <<'EOF'` promote with exit 0 into wrong recipes and the working fragment is marked superseded. Fix: refuse any heredoc `RUN` whose line holds more than `RUN <<['"]?NAME['"]?`, or keep the line command with the body.
